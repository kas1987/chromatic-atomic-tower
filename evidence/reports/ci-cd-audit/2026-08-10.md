## Executive result

CAT's core local validation is healthy, but the delivery control plane is not
yet aligned with the current Ways of Working. The most important gap is remote
enforcement: `master` requires only `validate` and `cat-ci`, has no required
review approval, does not require conversation resolution, does not enforce
rules for administrators, and does not require the Governance or LOGHOUSE
checks that are presented as authoritative controls.

Overall grade: **C**

- Observability: **C** — local checks and artifacts exist, but self-monitor
  output is advisory/unuploaded and three live GitHub workflow registrations do
  not have local source files.
- Transparency: **D** — branch protection does not enforce the documented human
  gate and several workflows/docs still name retired missions or `main`.
- Efficacy: **C** — recent runs are green, but duplicated suites, bypassable
  local hooks, and incomplete required-check coverage weaken confidence in the
  result.

## Findings

### F-001 — High — Remote promotion gates are weaker than CAT policy

GitHub `master` protection reports required contexts `validate` and `cat-ci`
only. Required reviews are absent; conversation resolution is disabled; admin
enforcement is disabled; and Governance/LOGHOUSE are not required. This means
an administrator or a PR that passes only the two legacy contexts can bypass
the broader documented control plane.

Recommended slice: make the canonical required-check set explicit, require at
least one human approval for governed changes, require conversation resolution,
and enforce the policy for administrators. Verify the result with a protected
branch negative test.

### F-002 — High — Workflow hardening is warning-only and currently fails strict mode

The cost guard reports 17 warnings across the eight local workflows: missing
explicit permissions, missing concurrency cancellation, and missing job
timeouts. The guard is not invoked by the current `validate-cat.yml`, although
the documentation says it is.

Recommended slice: add least-privilege permissions, concurrency groups, and
timeouts to every workflow; run `cat_cost_guard.py --check --strict` as a
blocking check for workflow changes.

### F-003 — High — Stale branch, mission, and sprint references remain in live controls

`cat-ci.yml` pushes only on `main` while the default branch is `master`.
Promotion/evidence workflows hard-code closed A006/A007/A010 mission IDs, and
the tower sprint goal still describes the already-closed A021 PR revalidation.
These references can produce valid-looking but misattributed evidence.

Recommended slice: parameterize evidence by event/PR HEAD and current mission,
remove retired defaults, and add a stale-reference test that compares workflow
constants and operating docs with the mission registry and default branch.

### F-004 — High — The local pre-push hook is not repository-portable or authoritative

`.git/hooks/pre-push` is untracked and delegates to
`$HOME/.claude/hooks/pre-push.sh`. It fails closed when absent, but can be
bypassed with `--no-verify`, and neither its source nor its install contract is
reviewable from CAT. Branch protection also permits administrator bypass.

Recommended slice: version the hook logic and installer under an allowed
tooling path, add a hook smoke test, and make remote branch protection—not the
local hook—the authoritative enforcement boundary.

### F-005 — Medium — Full test and governance work is duplicated across workflows

`cat-ci`, `cat-governance-ci`, `cat-loghouse-ci`, and `validate-cat` each run
the full pytest suite on PR/push paths; GitHub Bridge also runs the full test
tree. This increases cost and evidence noise without proving independent
invariants.

Recommended slice: define one canonical PR test job, keep only targeted
specialist jobs for Loghouse/bridge contracts, and make artifact ownership
explicit.

### F-006 — Medium — Self-monitoring is advisory and its output is discarded

LOGHOUSE self-monitoring runs without `--strict`, uses `continue-on-error`, and
writes to `/tmp/loghouse_self_output`, which is not included in the upload
paths. A self-monitor failure can therefore be invisible to reviewers.

Recommended slice: upload the self-monitor output, fail protected-branch runs
on P0/P1 findings, and label advisory runs as non-gating telemetry.

### F-007 — Medium — Dynamic GitHub workflows lack local ownership and provenance

GitHub lists active `Codex Review`, `Copilot`, and `Dependency Graph` workflows
whose source paths are dynamic or absent from the checkout. Their triggers,
permissions, versions, and lifecycle owner are not covered by local review.

Recommended slice: maintain a generated inventory of all live workflow IDs and
declare each dynamic integration's owner, permissions, trigger, retention, and
disable/deprecation path.

### F-008 — Low — Instruction and implementation surfaces drift

The CI governance docs say the workflow runs on `main`; the active default is
`master`. GitHub Actions guardrail docs claim the cost guard is called by
`validate-cat.yml`, but it is not. These are small individually but make audits
and operator decisions less reliable.

Recommended slice: choose one canonical CI contract and add a documentation
drift test for workflow names, branch triggers, and required commands.

## What worked

- CAT schema, alignment, repository, PR-guard, and local CI checks are
  executable and currently green.
- The resolver correctly reports idle state instead of inventing work.
- Required `validate` and `cat-ci` contexts are strict enough to catch the
  basic repository/test path.
- Recent remote runs are observable by exact HEAD and uploaded artifacts.

## What did not work

- The strict cost policy is not a gate.
- Human review and several advertised gates are not remote branch requirements.
- Static workflows still carry historical mission IDs and branch assumptions.
- The local hook is environment-owned and bypassable.
- Self-monitor evidence is not durable or blocking.

## Remediation order

1. Fix remote protection and required-check coverage (F-001).
2. Canonicalize workflow triggers/evidence identity and remove stale constants
   (F-003, F-008).
3. Enforce workflow hardening and strict cost guard (F-002).
4. Make hooks reproducible and remote enforcement authoritative (F-004).
5. Consolidate duplicated CI and preserve self-monitor evidence (F-005, F-006).
6. Register and own dynamic GitHub workflows (F-007).

This report is read-only audit evidence. No workflow, hook, branch-protection,
secret, PR, or mission state was changed by the audit.
